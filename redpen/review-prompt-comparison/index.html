Review prompts compared: AgentRun, roborev, and Red Pen's agent

Compares the verbatim prompts in agentrun-code-review/ (template 0.4.0) and roborev-prompts/ with Red Pen's own agent prompt (redpen_core::agent::prompt, crates/core/src/agent.rs). Based on reading those files; neither tool was run.

What each one is #

AgentRun code-review roborev Red Pen agent
Job Unattended: review every PR, post one review Review a commit, range or dirty tree; findings feed a fix loop Interactive: answer about the PRs in the queue, mark up the one you're on
Shape One orchestrator plus 8 parallel reviewers, then a merge One prompt assembled from shared sections, per-agent variants One long system prompt, one conversation per PR
Output One COMMENT review plus JSON findings Summary plus findings with severity, file/line, harm, fix Notes on lines (wrong/consider/note/house), suggested changes, tours, draft replies
Who posts The agent, to the forge The tool Never the agent: the user promotes a note or posts a draft

What the two review prompts share (and Red Pen's lacks) #

  1. A named bar for a finding. Both require a concrete failure: AgentRun a changed line and a named failure, roborev "what specifically goes wrong... concrete harm, not 'violates best practices'". Red Pen's prompt says use wrong only for a real problem, but gives no test for "real".
  2. An explicit do-not-report list. AgentRun's never-flag list and roborev's review_do_not_report both cut style, naming, speculative "missing tests", and problems the change didn't cause. Red Pen has none, so a note's quality rests on the model's judgment.
  3. Severity defined by impact, with a trigger. roborev: High/Medium/Low, and a Medium or High needs a named trigger or it drops to Low. AgentRun: P0 only "for a failure that needs no assumption about the input", with worked examples. Red Pen's four note kinds are about tone and purpose, not impact.
  4. A verify pass before reporting. roborev: re-check each finding and keep it only with a reachable scenario; verify dependency claims against the pinned version. AgentRun: the orchestrator prints each finding's cited lines and may drop one only on a quoted contradicting line. Red Pen's prompt has no step like it.
  5. Prompt-injection stance. Both treat PR text as data (AgentRun: title, body, comments, file names; roborev: commit messages and PR descriptions) and refuse their claims of "tested" or "safe" as evidence. Red Pen's prompt says nothing about untrusted PR text, though its agent can't post and only edits Red Pen's own notes.
  6. Intent check. roborev holds the diff to the commit message or PR description ("a change that misses its own stated goal is a high-value finding"). AgentRun has no such pass. Red Pen has the PR in show, but nothing asks the agent to compare it with the diff.
  7. Removed behavior and callers. roborev has passes for "name the invariant a deleted line enforced and find where it is re-established" and "check callers against new preconditions". AgentRun's checklist covers both (dropped cases in refactors, a contract changed under a caller). Red Pen's prompt does ask for callers and tests, as suggestions about where to look, not as required passes.

Where they differ #

  • Parallelism. AgentRun spends 8 contexts (5 quick at ~30 calls, 3 deep at ~90) so independent readers catch different things, then merges by path, line within 10 and same failure. roborev is one pass per run, and uses repeated reviews and previous-review context instead. Parallel reviewers cost far more per PR.
  • Memory across pushes. AgentRun fingerprints each finding (<!-- fp: ... -->), treats a reply as a dismissal and records the last reviewed head. roborev feeds previous reviews and attempts back in as prompt sections. Red Pen already keeps notes, replies and resolve state in its database, which is the same idea with a better home.
  • Output discipline. AgentRun caps findings (10 total, P2 limited) and ranks by how many reviewers raised each. roborev says to report every verified bug regardless of count, and to include quality and testing findings only when clearly worth acting on.
  • Repo-local rules. AgentRun reads the repo's CODEREVIEW.md from the base commit, never the head, so a PR can't loosen its own rules. roborev injects project_guidelines. Red Pen reads docs/house-notes, which is the same mechanism; reading them from the base is worth checking.
  • Per-model variants. roborev ships separate Claude Code, Codex and Gemini templates. AgentRun targets one harness.

Ideas for Red Pen (not done; for you to pick from) #

Ordered by how little they cost.

  1. Add a do-not-report list and an impact-based note bar to redpen_core::agent::prompt (items 1 to 3 above). It is prompt text only, and it should reduce noisy wrong and consider notes the most.
  2. Add a verify line before the agent writes a wrong note: cite the line and a reachable scenario, or write it as consider. This is roborev's review_verify in Red Pen's vocabulary.
  3. Add the intent check: compare the PR description with the diff, and write a wrong note where it falls short.
  4. Tell the agent that PR text is data. It can't post, so the risk is low, but the notes it writes are shown to you and suggest can put code in front of you.
  5. Read docs/house-notes from the base ref, not the head, if it doesn't already.
  6. A "review this PR" command could fan out a few reviewers over Red Pen's existing tools (diff, search, definitions, read_file) and merge with AgentRun's rule: same path, nearby lines, same failure. This is the largest change and costs the most per PR.

Caveats #

  • AgentRun's agent.md lists get_repository_tree, which GitHub's hosted MCP server lacks.
  • roborev's templates are Go templates. The Go code that fills them in is not copied, so a few behaviors (what a "previous review" or "toolchain" section contains) are inferred from template names.
  • Nothing here measures quality. For that, use a benchmark on your own PRs.
