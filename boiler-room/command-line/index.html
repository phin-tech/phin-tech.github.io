The command line and agents

Everything the window does, boiler-room does in a terminal, and agents use it too. Help › Install Command Line Tool (or Welcome) puts it in ~/.local/bin: a link to the app's own binary, which answers a command line before opening anything. By hand, that's:

ln -s "/Applications/Boiler Room.app/Contents/MacOS/Boiler Room" \
    ~/.local/bin/boiler-room

Looking #

boiler-room status               # the service, and what to install
boiler-room service status       # running, which version, and whether it starts at login
boiler-room service restart      # restart it, saying each step; start, stop and login-items too
boiler-room service run          # without a login item, until you log out: for a Mac IT manages
boiler-room service test --slaps # a test notification, and a test Slaps alert
boiler-room service settings     # daemon.toml's path, made if missing; --edit opens it
boiler-room settings host tmux   # set one of the daemon's settings; with only a name, its value; --unset
boiler-room jobs                 # every Job and Errand, and how it went
boiler-room runs aws-case-1234   # its newest Runs
boiler-room show 42              # one Run: output, errors, values, report
boiler-room templates            # Templates and their Params
boiler-room questions            # what's waiting for you

--json on most of them gives something to parse.

Doing #

boiler-room run aws-case-1234 --wait    # now, and exit as it did
boiler-room new aws-case case=1234      # a Job from a Template
boiler-room schedule aws-case-1234 3h   # or a cron line in quotes
boiler-room pause aws-case-1234         # and resume; stop <run>
boiler-room archive aws-case-1234       # put a Job away, file and Runs kept; unarchive brings it back
boiler-room answer 3 yes                # a question
boiler-room submit --every 30s -- gh pr checks 123

From Alfred #

Settings ▸ Integrations (or Help ▸ Install Alfred Workflow) packs the workflow and opens it, and Alfred (with its Powerpack) asks you to import it. just alfred does the same into target/Boiler Room.alfredworkflow. Type br and part of a Job's name: ⏎ runs it now, ⌘⏎ shows it in the app. br also lists Show the Dashboard and New Job, and brd opens the Dashboard directly. It runs the command line, so install that first; the workflow looks for ~/.local/bin/boiler-room, then the app's own copy, and a workflow variable named boiler_room overrides both. It opens the app through boiler-room://dashboard, …://new and …://job/<id>; running a Job is the command line's, never a link's, as a web page can open a link.

From a Script #

Inside a Run, a Script reports with notify, changed, unchanged, value, report, progress and step, and asks with ask, confirm, wait and choose (Being told); gum file and gum table ask for a path or a row (the Python and JavaScript libraries have file and table too, below). Outside a Run they refuse, unless given --job to try a Script by hand.

In Python or JavaScript #

A Python or JavaScript Script can report with a library instead of starting boiler-room for each call. Each is one file with no dependencies, and talks straight to the Daemon.

import boiler_room as br

br.step("Check the case")
br.value("status", "Pending AWS", tone="warn", icon="clock")
if br.confirm("Rotate the key?"):
    br.notify("Rotating", loud=True)

import { pathToFileURL } from "node:url";
const br = await import(pathToFileURL(process.env.BOILER_ROOM_JS).href);

await br.step("Check the case");
await br.value("status", "Pending AWS", { tone: "warn", icon: "clock" });

Both have notify, changed, unchanged, value (with its Gauge look), report, progress, step, again, ask, confirm, wait, choose, file and table, and param, state_dir, job and forced for where the Script is (param, stateDir, job, forced in JavaScript, where each call is awaited). In a Run, Python's import boiler_room just works, and $BOILER_ROOM_JS names the JavaScript file. Outside a Run the report calls refuse, and BOILER_ROOM_DRY_RUN=1 prints what they would have sent, to try a Script by hand.

To use them in a Script that runs elsewhere, boiler-room python and boiler-room js print the files. With uv, a Script can declare the library in its own header, or you can try one with uv run --with /path/to/Boilerroom/crates/cli/python check.py; for JavaScript, save boiler-room js beside the Script as boiler-room.mjs.

Agents #

boiler-room mcp is an MCP server, for Claude Code or any agent: it lists and reads Jobs, Runs and Templates, makes Jobs, runs them, changes schedules, hands over Errands and waits for them, and answers questions (never a hidden one). Tools that change something say so. To add it to Claude Code:

claude mcp add boiler-room -- boiler-room mcp

boiler-room skill prints a Skill that teaches an agent how to use all of this; save it as ~/.claude/skills/boiler-room/SKILL.md.

The daemon's settings #

~/.config/boiler-room/daemon.toml, read as it changes. boiler-room status says if it can't be read, and the defaults are used meanwhile. Settings › Where Jobs Run changes each of them, as boiler-room settings <name> <value> does (boiler-room settings hosts.tmux.session work), keeping any comments in the file.

# What reads a Job's `run` line: your login shell, or a program, as "/bin/sh"
shell = "login"
host = "tmux"              # where a Job runs that doesn't say; "pipes", no terminal, if left out

[hosts.tmux]
session = "boiler-room"    # the session tmux Runs open windows in

[hosts.zellij]
session = "boiler-room"

[hosts.hc]
machine = "vps"            # hc Runs start there, as `hc run --on vps`

[runners.<name>] says what reads a Job's script (runner = "<name>"). uv, python3, node, bun and deno come with the app; a key here replaces theirs, and a new name adds a runner. These are edited in the file, not with boiler-room settings.

[runners.deno]
command = ["deno", "run", "--allow-net", "{file}"]   # {file} is the script's path
ext = "ts"                                           # the script file's extension, which Deno and Node read

[runners.tsx]
command = ["npx", "tsx", "{file}"]
ext = "ts"
env = { NODE_NO_WARNINGS = "1" }                      # variables its Scripts get; a Job's env is over them
